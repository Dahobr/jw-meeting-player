# 再生同期と自動再生制御の不具合修正記録 (2026-05-03)

## 1. セカンドモニターでの動画再生同期不全

### 問題
メインウィンドウで動画を再生しても、セカンドモニターが待機画面（年間聖句）から動画に切り替わらない。画像（待機画面）は表示されるが、動画のみ信号が伝わっていない状態。

### 原因
1.  **IPC通信でのデータ欠落:** `displayManager.js` の `load-media` リスナーが、`mediaPath` と `mediaType` のみを受け取り、`autoPlay` や `startTime` などの制御情報を捨てていた。
2.  **プロトコル実装の不備:** `main.js` の `media://` プロトコルハンドラが、エラー時にオブジェクトを返していた（設計指針ではパス文字列または数値を返す必要がある）。
3.  **セッションの不一致:** セカンドモニターの `BrowserWindow` がメインウィンドウと同じセッション（`persist:jw_session`）を使用していなかったため、プロトコル登録が正しく認識されない場合があった。
4.  **競合するエラー判定:** `playback.js` 内でビデオ再生開始時に画像をリセット（`src=""`）した際、画像の `onerror` が発火し、エラー画面で上書きされていた。

### 処置
-   `displayManager.js`: 受信したデータをオブジェクトごとセカンドモニターへ転送するように修正。
-   `main.js`: プロトコルハンドラを修正し、常に文字列または数値を返すように変更。
-   `displayManager.js`: `playbackWin` の作成時に `partition: 'persist:jw_session'` を指定。
-   `playback.js`: 空の `src` による `onerror` を無視するようにガードを追加。

## 2. スタンバイ時のプレビュー動画勝手な自動再生

### 問題
画像を表示させた直後に動画をクリックしてスタンバイ（プレビューのみ）させると、プレビュー画面で動画が勝手に再生されてしまう。

### 原因
-   **イベントリスナーの消し忘れ（ゴースト・リスナー）:** `goLive` 実行時に `canplay` リスナーを登録していたが、読み込み完了前にメディアを切り替えたり停止したりしても、そのリスナーが解除されずに残っていた。次に動画を読み込んだ際、古いリスナーが発火して `play()` を呼び出していた。

### 処置
-   `app.js`: `this.pendingCanPlayListener` 変数を導入し、リスナーの参照を保持。
-   `prepareStagingMedia`, `goLive`, `stopMedia`: 新しいメディアを扱う前や停止時に、必ず既存の `canplay` リスナーを `removeEventListener` で解除するように徹底。

## 3. 自動スタンバイ機能の実装

### 機能概要
プレイリスト操作を効率化するため、以下の自動化を実装。
- プレイリスト選択時、最初のアイテムを自動スタンバイ（読み込み）する。
- 再生終了または停止時、自動的に「次のアイテム」をスタンバイする。リストの最後の場合は最初のアイテムへループする。

### 実装内容
- `app.js` に `staged` ステータスを導入し、動画の一時停止と区別。
- `stopMedia` に再入防止ガード（`isStopping`）を導入し、無限ループを阻止。
- UI 状態の正確な管理と視覚化。

### UI 改善
- スタンバイ中のアイテムを明確にするため、配色を調整。
- 背景を薄い琥珀色 (`rgba(243, 156, 18, 0.2)`) にし、ボタンアイコンと枠を柔らかいオレンジ (`#e67e22`) に設定。これにより他状態と明確に区別できるようにした。

## 4. BrowserView からの画像ダウンロード不全の解消 (2026-05-03 追加)

### 問題
WOL などの外部サイトにおいて、Akamai 等のボット対策により `downloadURL` による再リクエストがブロックされ、画像がダウンロードできない（または 403 Forbidden となる）。

### 原因
- **セッション情報の不完全な引き継ぎ:** `downloadURL` が発行するリクエストにおいて、BrowserView のレンダリングコンテキストが保持している Cookie やセッション状態が完全に引き継がれず、サイト側から「不正なアクセス」と判定されていた。

### 処置
- **メモリ内抽出方式の採用:**
  - `main.js` から `executeJavaScript` を使用し、BrowserView のドメインコンテキスト内で `fetch()` を実行。
  - 取得した画像データを `Blob` 経由で Base64 文字列に変換してメインプロセスへ返却。
  - `downloadManager.js` にて Base64 を Buffer に戻してファイルとして保存。
- **利点:** ブラウザが既に認証済みのセッションをそのまま利用するため、追加の認証やボット判定に阻まれることなく、表示されている画像を確実に保存できる。
- **留意点:** 動画に関してはサイズが大きいため、引き続き `downloadURL` を使用する（コンテキストメニューで処理を分岐）。

## 教訓と今後の指針
-   **非同期イベントの管理:** `addEventListener` を使う際は、必ず対になる `removeEventListener` のタイミング（切り替え、停止、エラー時）を考慮すること。
-   **データの完全性:** メインプロセスを経由する通信（中継）では、将来の拡張性も含め、データを不用意にフィルタリングせずオブジェクトごと渡すことを優先する。
-   **設計指針の遵守:** `docs/tech-notes/` にある設計指針（プロトコルの戻り値型など）は、Electronの低レイヤー動作に直結するため厳守すること。
-   **ボット対策サイトへの対応:** 外部サイトからのリソース取得で 403 エラー等が出る場合は、再リクエスト（URL指定）を避け、表示中のコンテキストからデータを直接抽出（executeJavaScript + fetch/Blob）する手法を検討すること。
